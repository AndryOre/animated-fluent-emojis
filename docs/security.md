# Security

This document is the assurance case for `animated-fluent-emojis`: what the
library fetches at runtime, who it trusts, what that means for your Content
Security Policy, and where its defenses fall short today. It is written for
consumers and security reviewers. Terms such as asset site, slim manifest and
sprite sheet follow [`CONTEXT.md`](../CONTEXT.md).

To report a vulnerability, see [`SECURITY.md`](../.github/SECURITY.md). This
document covers the design, not the reporting process.

## Threat model

The library renders `<img>` elements through a component for each supported
framework. The React, Vue, Svelte, Astro and vanilla adapters inject no
`<style>` element, and everything per-emoji is an inline style on the image (see
[architecture](architecture.md#component)). The `<fluent-emoji>` element is the
exception: it adds one `<style>` element to its own shadow root. Its network
surface is two kinds of request, both to the asset site:

- One fetch of the slim manifest, made the first time an emoji needs it, never
  at import time.
- One sprite sheet image per emoji and skin tone, loaded through an `<img>`.

The threats worth reasoning about follow from that surface:

- **A compromised or altered asset site** serves a manipulated slim manifest or
  different sprite sheets than the ones the pipeline built.
- **A compromised release** puts a malicious version of the package on npm.
- **An unavailable asset site** stops emojis from rendering. This already
  happened once, when a custom domain lapsed
  ([ADR 0006](adr/0006-cloudflare-pages-asset-hosting.md)).
- **A poisoned build input** reaches the asset site through the sync pipeline.

## Trust boundaries

| Party                        | What it controls                                                                                                            | How far it is trusted                                                                                         |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| The consumer app             | Where the component renders, the CSP, and the optional `assetSiteUrl` passed to `configureEmojis`.                          | Fully. It decides which asset site the library talks to.                                                      |
| The npm package              | The code that runs in the app and the default asset site URL, `https://animated-fluent-emojis-cdn.andryore.dev`.            | As any dependency. Releases are built from a signed tag with provenance (see Supply chain below).             |
| The asset site               | The slim manifest at `/v1/manifest.slim.json` and the sprite sheets under `/v1/sprites/`.                                   | As the source of what the library renders. The library does not verify what it serves.                        |
| The files site               | The public GIF, WebP and PNG files, the public index (`/index.json`) and `/version.json`. The library never loads them.     | Not at all by the library. People download or hotlink the files; consumers of the files choose to trust them. |
| Microsoft's upstream artwork | The Teams emoticon manifest and Microsoft's MIT-licensed `microsoft/fluentui-emoji-animated` repository the pipeline reads. | As the source of the artwork. The pipeline validates the files it generates, not the upstream itself.         |

The asset site is generated by `scripts/assets` and published by
`.github/workflows/sync-assets.yml`. Nothing it produces is committed to the
repository ([architecture](architecture.md#asset-site)). A sync that reuses
sprite sheets downloads them from the live asset site, so the build trusts the
published site as its own previous state
([ADR 0010](adr/0010-versioned-asset-layout-and-live-seeding.md)). Reused files
go through the same validation as built ones.

The files site is a second Cloudflare Pages project, built from the asset site
by the same workflow. Its files are public downloads and the library does not
use it at runtime, so it adds no request to a consumer's CSP. A sync merges the
live public index into the slug registry before a build, so published file URLs
never change. A compromised files site can serve altered files to people who
link them, but cannot change what the library renders.

## CSP requirements

With the default asset site, a consumer that sets a Content Security Policy
needs:

- `connect-src https://animated-fluent-emojis-cdn.andryore.dev`, for the
  manifest fetch.
- `img-src https://animated-fluent-emojis-cdn.andryore.dev`, for the sprite
  sheets.

The sprite URL is `<site>/v1/sprites/<category title>/<id><tone>.<etag>.png`,
with `@2x` before the extension for an HD sprite sheet, so one origin covers
both.

The previous address, `https://animated-fluent-emojis.pages.dev`, keeps working.
If you upgrade with a strict CSP written for it, add the new host to both
directives, because the library now requests the `andryore.dev` address.

When you pass a different `assetSiteUrl` to `configureEmojis`, use that origin
in both directives instead. To host the asset site yourself, follow
[how to set up asset hosting](how-to/set-up-asset-hosting.md), then point
`configureEmojis` at it. That keeps both directives on an origin you control.
Call `configureEmojis` before the first `Emoji` renders.

Because the React, Vue, Svelte, Astro and vanilla adapters add no `<style>`
element, they need no `style-src` allowance for injected styles. The
`<fluent-emoji>` element adds one to its shadow root, so a strict `style-src`
needs an allowance for it (a nonce or `'unsafe-inline'`), or use another
adapter.

## Supply chain

- **Trusted publishing.** `release.yml` publishes from a pushed signed `v*` tag,
  in the `npm` GitHub Environment, with `id-token: write`. npm authenticates the
  workflow through OIDC, so no `NPM_TOKEN` is stored, and provenance is
  generated automatically. The workflow re-runs `bun run check`, `bun run test`
  and `bun run build` before it publishes
  ([ADR 0005](adr/0005-npm-trusted-publishing.md)).
- **Immutable releases and protected tags.** A published GitHub Release cannot
  be edited, and the `v*` ruleset blocks tag deletion and updates, so a bad
  release is fixed by a new version
  ([ADR 0001](adr/0001-public-repo-security-posture.md)).
- **SHA-pinned actions.** `sha_pinning_required` makes every `uses:` reference a
  full commit SHA, and Renovate keeps the pins current. Workflows are linted
  ([development](development.md#ci)).
- **Protected `main`.** A ruleset blocks force-pushes and deletion and requires
  a pull request, linear history, signed commits and the `CI passed` check
  ([ADR 0001](adr/0001-public-repo-security-posture.md)).
- **OpenSSF Scorecard** runs on a schedule and on push to `main`, published with
  a README badge. CodeQL runs through the default setup.
- **Renovate** is the single source of dependency updates; Dependabot updates
  are not used ([ADR 0001](adr/0001-public-repo-security-posture.md)).
- **No state carried between sync runs.** The Actions cache was removed for
  cache-poisoning reasons
  ([ADR 0010](adr/0010-versioned-asset-layout-and-live-seeding.md)).
- **Sync guards.** A sync fails before it deploys when the Teams discovery finds
  no metadata hash, when more than 5% of the previous catalog would be removed,
  or when the output has more than 19,000 files
  ([architecture](architecture.md#sync-guards)).

## Secure-design principles

- **Nothing at import time.** The manifest is fetched lazily, and the server
  snapshot is always `loading`, so server and client markup match
  ([architecture](architecture.md#manifest)).
- **Bounded requests.** The manifest fetch gives up after 15 seconds and is
  retried like any error ([architecture](architecture.md#manifest)).
- **Failure stays contained.** A failed sprite load shows the fallback glyph or
  the `fallback` you provide, and `onError` reports the failure
  ([architecture](architecture.md#fallback)).
- **Manifest ids are plain keys.** The manifest record has no prototype, so ids
  such as `constructor` or `__proto__` are ordinary keys
  ([architecture](architecture.md#manifest)).
- **Immutable URLs.** The etag is part of the sprite file name, so a URL never
  changes meaning, and the previous sprite generation stays published for one
  more sync ([ADR 0010](adr/0010-versioned-asset-layout-and-live-seeding.md)).
- **Validate before publishing.** `validate.ts` checks the planned catalog and
  the generated files before anything is published
  ([architecture](architecture.md#asset-site)).
- **No standing npm credential.** The release uses OIDC. The asset site deploy
  needs the Cloudflare secrets documented in
  [how to set up asset hosting](how-to/set-up-asset-hosting.md).

## Known limitations

- **No Subresource Integrity on runtime fetches.** The slim manifest is fetched
  without an integrity check, and the sprite `<img>` elements carry none. A
  compromised asset site can change what the library renders. Content-addressed
  sprite file names make URLs immutable, but they do not prove the bytes.
- **The asset site is a single origin.** The default asset site is one
  Cloudflare Pages project. If it is unavailable, emojis render your `fallback`
  node, or nothing when none is given: the fallback glyph comes from the
  manifest, so it cannot show when the manifest itself failed. Self-hosting is
  the alternative (see CSP requirements above).
- **The sync trusts the live site and Microsoft's upstream.** Seeding reuses
  sprite sheets from the published site, and the artwork comes from the Teams
  emoticon manifest and Microsoft's MIT-licensed repository. The pipeline
  validates the files it produces, not the upstream itself.
